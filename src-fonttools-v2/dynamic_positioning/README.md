# dynamic_positioning — geometry-derived GPOS for right-hand-technique words

**Status: experimental prototype, not the final design.** Fully covers
`gou` (`lg_gou`/`lg_da`), `io` (`lg_ti`/`lg_zhai`), and `li` (`lg_li`) —
replacing `layout_gou/gou2/gou3`, `layout_io/io2/io3`, and
`layout_li/li2/li3` with literal `pos` rules generated from a declarative
table (`geometry.py`) instead of hand-tuned Figma layout frames. Also has
an early, incomplete start on `cuo` (撮 chords: `chord_left`/`chord_right`
in `geometry.LAYOUTS`, keyed on `C`/`DC`/`FC`/`TT`/`|`) — see "cuo: current
status" below before relying on it — and a similarly early start on
vert-mode (`:`-triggered stacked-row words: a `"vert"` `LAYOUTS` entry,
still being built out in `tools/jzpbuilder-dynamic.html` as of this
writing, staged in sidecar files like `layouts_data.vert2.json` — see
"Adding a custom signifier"'s worked example and "Repeated-slot areas"
below for how its `char_1`/`char_2`/`fy_1`/`fy_2` stacking works). All
other layout families (`loki`, `nc`, `tiao`, `mo`) are untouched and still
generated by `jzpbuild/gpos.py::gen_gpos()`.

Opt in with `python3 -m jzpbuild --dynamic_pos`. There's also
`--dynamic_pos_only`, which additionally zeroes out every classic-
positioned shape this module *doesn't* cover (other right-hand families,
vertical-mode words, cuo chords) so they render visibly broken instead of
silently working via classic — useful for checking this module's actual
coverage without classic quietly filling the gaps. Both flags are plumbed
through `jzpbuild/genfea.py` → `jzpbuild/gpos.py` (`gen_gpos`'s
`skip_right_keys`/`zero_others` params) and are fully reversible: nothing
in `dynamic_positioning/` is imported unless one of these flags is passed,
and neither flag touches `jzpbuild/features.py` (GSUB) at all — plain
`jzpbuild` is unaffected regardless of anything in this directory.

## Why not GPOS mark attachment (an earlier version of this used it)

The first version of this prototype used GPOS mark-to-base/mark-to-mark
anchors (types 4/6): `area_fy` as a base, `area_hui`/`area_left`/`area_jc`/
`area_zhu`/`area_right` chained on as marks, so an absent element simply
didn't attach — no separate layout needed per jc/hui presence.

That broke as soon as it was tested against a non-gou/io word. `fy`, `hui`,
`left`, `jc`, `zhu` are the *same shared glyphs* across every right-hand
family, not gou/io-specific variants — so the mark rules fired (and
additively stacked on top of) the classic pipeline's own positioning for
`loki`/`nc`/`tiao`/`mo`/`li` words too, since GPOS single-adjustment value
records accumulate across lookups. Confirmed empirically: `fylo3` (fy +
loki + string) rendered `mod_fanyin` at roughly double its correct offset.
Mark attachment has no way to require "and only within a gou/io word" —
anchors fire wherever the glyph shapes match, full stop.

Literal contextual single-adjustment rules (GPOS type 1, chained context)
*can* require an exact backtrack/lookahead sequence, including a specific
per-signifier class (see "Scoping" below) — the same mechanism
`jzpbuild/gpos.py::word_layout_rules()` already relies on for correctness
(every rule it emits, including `fy'` ones, ends with the right-hand
family's own class as trailing context). So this module generates the
same *kind* of rule classic does, just computed from `geometry.py`'s
declarative data instead of authored per Figma layout.

## Structure

- `geometry.py` — pure data, but not a Python literal: `AREA_SIZES`,
  `CENTER_X`/`CENTER_Y`, and `LAYOUTS` are loaded at import time from
  `dynamic_positioning/layouts_data.json` (`config.DYNAMIC_LAYOUTS_JSON`),
  so `tools/jzpbuilder-dynamic.html` (see "Visual editor" below) can edit
  and save this data without touching Python source. Each `LAYOUTS` entry's
  `"areas"` is re-attached as the *same shared* `AREA_SIZES` dict object —
  editing one area's size in the JSON/editor affects every topology that
  references it. `anchors.py`/`chain.py`/`build.py`/`classes.py` don't care
  that this is JSON-backed; they only ever read `layout["areas"]`,
  `layout["relationships"]`, `layout["order"]`, `geometry.CENTER_Y`.
- `signifiers.py` — ASCII-key ↔ glyph mapping, derived from
  `components.csv` (read-only, via `jzpbuild.data`) plus a small
  supplementary table for glyphs that live outside `components.csv`
  entirely (control glyphs like `blank_bar`). The finest-grained unit this
  module addresses — one step below `config.RIGHT_SELECTORS`' families
  (e.g. `gou` → `k` for `lg_gou`, `l` for `lg_da`, independently). Also
  provides `AREA_TO_CSV_COLUMN` (dynamic-positioning area name →
  `components.csv` area column, e.g. `hui` → `area_hui`, `jc` →
  `area_mod_jc`) plus `csv_column_for(area)`, the generalization
  `identity.area_glyphs`/`classes.gen_repeated_area_classes` actually call
  — falls back to stripping a trailing `_N` when `area` itself isn't
  registered, so `"char_2"` resolves via `"char"`'s own column (see
  "Repeated-slot areas" below) — the single source of truth `identity.py`,
  `build.py`, and the JS editor all share for "which glyphs can occupy
  this area."
- `identity.py` — for one `LAYOUTS` entry, scans its `relationships` for
  every glyph name any gap override's `"base_signifiers"`/`"elem_signifiers"`
  lists reference, attributing each to that relationship's own `base`/`elem`
  **area** directly (no `components.csv` scan needed for this part) and
  reporting exactly which glyphs of that area are referenced (plus whether a
  catch-all applies) — see "Gap overrides can key off any area's glyph
  identity" below. Shared by
  `classes.py` (class generation) and `build.py` (rule branching) so the
  two agree by construction on which areas get their own glyph-identity
  classes.
- `anchors.py` — `AnchorEngine`: a generic engine that resolves one
  `LAYOUTS` entry's relationships into coordinates. One instance per
  entry (see `build.py`'s `_ENGINES`). No hardcoded area names or
  per-pair formulas anywhere in this file.
- `chain.py` — resolves one word combination through one `AnchorEngine`:
  a genuinely generic dependency-graph walk (not a fixed sequential
  chain — see "Three orderings" below), then applies a whole-stack
  **vertical centering shift** (see below) so the composed character is
  centered on `geometry.CENTER_Y` regardless of which optional elements
  are present.
- `classes.py` — generates one FEA glyph class per (family, key)
  signifier for the **pivot** area (e.g. `@area_right__gou__lg_gou` vs
  `@area_right__gou__lg_da`), separate from `jzpbuild/features.py`'s
  shared per-*family* classes — plus, via `gen_area_glyph_classes()`, one
  class per (layout, area, glyph) any *non-pivot* area's gap override
  references, and a catch-all "every other glyph in this area" class when
  a catch-all override is declared (see `identity.py` above).
- `build.py` — drives everything off `geometry.LAYOUTS`: for each entry,
  for each key in its `selector.contains`, enumerates every optional-
  element presence-combination, and — for each present non-pivot area
  `identity.py` flags as glyph-identity-sensitive — further branches over
  that area's declared glyph buckets (see below), generates one literal
  `pos` rule per (combination, bucket-choice, positioned element) pair
  with the value computed by `chain.py`, sorts most-specific-first, and
  adds the explicit "blocker" rule that keeps `area_fy`'s positioning from
  leaking into words this module doesn't cover.

## `geometry.LAYOUTS`: one entry per topology

A *topology* is a distinct spatial-adjacency shape. `gou`/`io`/`li` all
share one (`"default_jzp"`) — they're differently-proportioned
*signifiers* within the same fy/left/hui/jc/right/zhu/string shape, not
different shapes. A genuinely different shape (no `area_right`-equivalent
pivot at all, or a repeated structure) needs its own `LAYOUTS` entry.
Shape of one entry:

```python
{
    "name": "default_jzp",
    "selector": {"contains": ["k", "l", "i", "o", "U"]},   # ASCII keys, see signifiers.py
    "areas": AREA_SIZES,                                    # per-area (w, h)
    "vertical_center_order": [["fy"], ["left", "hui"], ["jc"], ["zhu"], ["right"]],
    "relationships": RELATIONSHIPS,
    "order": [
        {"area": "fy", "optional": True},
        {"area": "left", "optional": True},
        {"area": "hui", "optional": True},
        {"area": "jc", "optional": True},
        {"area": "zhu", "optional": True},
        {"area": "right", "optional": False, "pivot": True},
        {"area": "string", "optional": False},
    ],
}
```

- **`selector.contains`** — which ASCII keys route to this topology.
  `build.py`'s `_engine_for_key` is the *only* place that reads this;
  everything downstream only ever sees whichever single `AnchorEngine` it
  was built for. (There's no `"startsWith"`-style prefix selector kind
  implemented yet — cuo/vertical-mode's real dispatch is a leading
  character, not glyph presence, but `chord_left`/`chord_right` below are
  wired in today via ordinary `contains` on their pivot's own key, not a
  true prefix match. Revisit if/when this actually matters.)
- **`relationships`** — the spatial-adjacency graph (`RELATIONSHIPS`'
  shape, see below).
- **`vertical_center_order`** — visual top-to-bottom *rank* order, used
  **only** for the whole-stack Y-axis centering shift. Same-rank groups
  (`["left", "hui"]`) sit side by side; either may define that rank's box.
  Not the same as `order` (below) or `relationships`' own dependency
  structure — a genuinely different fact (which elements share a row on
  screen), and the three orderings aren't guaranteed to agree, even
  though they do for `default_jzp`.
- **`order`** — the real typed/glyph-sequence fact: which elements are
  optional (drives `build.py`'s presence-combination enumeration and
  backtrack/lookahead construction) and their real sequence position.
  Flat, no sibling grouping needed — typing is inherently sequential (you
  can't type `left` and `hui` "at the same time"), and classic
  `gpos.py`'s own `_lh_combos()` confirms `left` always precedes `hui`
  when both are present, so there's no "either order" ambiguity to model
  here (unlike `vertical_center_order`, which is genuinely about visual
  rows, not typed order). `"optional": False` marks elements that are
  always resolved regardless of whether a given word actually has one —
  nothing later in the sequence needs to condition on a pure leaf's
  presence, and GPOS's own glyph-class matching already handles "did this
  glyph actually show up here" for free (see "Three orderings" below).
  `"pivot": True` marks the **one** always-present element whose glyph
  *is* the signifier itself (`right` for `default_jzp`, `chord`/`bar` for
  cuo) — gets `classes.signifier_token(...)` instead of the generic
  `"@area_{elem}"` token every other element uses. `AnchorEngine.__init__`
  raises if an entry's `order` doesn't mark exactly one pivot.

`RELATIONSHIPS` entry shape:

```python
{"axis": "x"|"y", "elem": <area>, "base": <area>|None,
 "base_edge": <edge>|omitted, "elem_edge": <edge>|omitted, "gap": Gap}
```

For `axis="y"`, edges are `"top"`/`"bottom"` (`base_edge` default
`"bottom"`, `elem_edge` default `"top"`). For `axis="x"`, edges are
`"left"`/`"right"` (`base_edge` default `"left"`, `elem_edge` default
`"right"`). `elem`'s `elem_edge` is placed at `base`'s `base_edge`
position plus `gap` (both expressed in `base`'s own local coordinates,
its own origin at its near corner). Both edge fields are almost always
left at their default — write them out explicitly only when a
relationship genuinely needs the other edge (`anchors.py::anchor()`).
`base=None` means "no dependency" — `gap` is then the literal absolute
default value directly, not a relative offset.

`gap` shape: a plain number (same regardless of glyph identity), or an
ordered list of override entries `{"base_signifiers": [...],
"elem_signifiers": [...], "value": <number>}` (either or both signifier
keys omittable), evaluated **first-match-wins in list order** — not "most
specific wins": an entry with neither key is an unconditional catch-all
and must be placed last by the author, nothing enforces that ordering
(`anchors.resolve_gap`). **Signifier entries are literal `components.csv`
`glyph_name` values** (`"lg_gou"`, `"lg_da"`, `"md_5"`, ...), not ASCII
keys — `glyph_name` is unique per row by construction, unlike
`keys`/`latin`, which can collide across areas (e.g. `"0"` means both
`md_san` in `area_hui` and `md_san2` in `area_char`).

`"base_signifiers"` matches the relationship's own `base` area's glyph;
`"elem_signifiers"` matches its `elem` area's glyph — independent
conditions, so one entry can constrain either side alone, or both at once
for a genuine conjunction (e.g. "only when `hui` is `md_9` **and**
`right` is `lg_gou`"). This is what lets `lg_gou` and `lg_da` get
independently-tuned values instead of being forced to share one (classic's
own per-*family*, not per-glyph, granularity) — and, since either key can
name a glyph from any area the relationship touches, not just the pivot's,
it's also what lets e.g. a `jc`↔`hui` relationship's gap vary by which
specific `area_hui` glyph is present (via `base_signifiers`, since `hui`
is that relationship's `base`). See "Gap overrides can key off any area's
glyph identity" below for the general mechanism, and `resolve_gap`'s
docstring for the exact matching rule.

(This is a rename/split of an earlier flat `"signifiers"` field, which
matched against every glyph present anywhere in the word regardless of
which area it belonged to or which side of the relationship it was
conceptually on — functionally equivalent for every override that existed
under that scheme, since each one only ever referenced glyphs from
strictly the base or strictly the elem side, but it couldn't express a
conjunction across both, and "which side does this glyph belong to" was
inferred by scanning `components.csv` rather than being explicit.)

Most numeric gap values in `RELATIONSHIPS` are placeholders (an explicit
decision to prioritize getting the engine's shape right over re-deriving
exact classic-matching numbers this round) — expect to retune them
against `tests/test_shaping.py` and `font_tester.html`.

## Three separate orderings (don't conflate them)

This module tracks three genuinely independent facts about the same
handful of areas, and an earlier version of it conflated the first two,
which was a real bug (see "Fully generic `chain.py`" below):

1. **Typed/glyph-sequence order** (`LAYOUTS` entry's `order` field) — a
   fact about the input/shaped text. Used by `build.py` to build correct
   backtrack/lookahead context, and nowhere else.
2. **Attachment/dependency order** (`RELATIONSHIPS`' own `base` pointers)
   — a pure geometry/authoring choice: which element's *position* is
   computed relative to which other element's. `chain.py` resolves this
   as a dependency graph, not a walk over (1).
3. **Centering rank order** (`vertical_center_order`) — which elements
   share a visual row, for the whole-stack recentering shift only.

For `default_jzp` these three happen to mostly agree (fy → left/hui → jc
→ zhu → right, typed in that order, each one attaching to whichever
optional predecessor came before it, stacked in that same visual order)
— but they don't have to, and `area_zhu` is the clearest example that
they don't: it's typed *before* `area_right` (fact 1), but its *position*
(fact 2) is computed as a pure offset from `area_right`'s already-resolved
position — a deliberate reversal from an earlier version of this module,
where `zhu` instead attached to whichever of jc/hui/left/fy preceded it.
Visually `zhu` sits right up against the technique glyph, so anchoring it
there (once the technique glyph's position is known) is a better match
for what it's actually doing. This only works because "typed order" and
"attachment order" are tracked separately — flipping the dependency
direction for one element while its glyph-sequence position stays fixed
would be impossible if the two facts were the same field.

## Fully generic dependency-graph resolver (`chain.py`)

No hardcoded element names anywhere in `chain.py`/`anchors.py`. Given a
word's presence flags (from `order`'s optional elements) plus every
always-present element a topology's `relationships` declare,
`chain._choose_relationships` picks, per element per axis, which
candidate relationship applies — preferring (most to least specific): a
candidate whose base is a *ranked* (optional, per `order`) element that's
actually present, highest-rank (most recently typed) first; then a
candidate whose base is a guaranteed-resolvable always-present element;
then the root (`base=None`) default as a last resort. This reconstructs
"attach to whichever optional element was typed most recently" without a
fixed sequential walk, and correctly falls back to the true typed-order
recency rule when multiple ranked candidates are simultaneously present
(e.g. `jc` attaching to `hui` rather than `fy` when both precede it,
because `hui` is ranked later in `order`).

One real bug found and fixed while building this: naively picking "the
first candidate whose base qualifies" in raw declaration order breaks,
because root (`base=None`) defaults are conventionally declared *before*
their overrides in `RELATIONSHIPS` — so that approach picked root every
time, silently ignoring presence entirely. Fixed by ranking candidates by
specificity rather than declaration order.

`resolve()` then walks the (now unambiguous) dependency graph to
completion — resolving whatever has no unresolved dependency first —
rather than assuming any fixed pass order, which is what actually makes
this generic across topologies with different shapes (`default_jzp`'s
fy→...→right→string chain vs. `chord_left`'s much shorter chord→jc→string
chain).

An always-present (non-optional) element is allowed to fail to resolve
for a given signifier — e.g. `string_top`/`string_bottom` have no
catch-all gap, so `KeyError` is *expected* for every signifier but `"U"`
(li). That's silently treated as "this element doesn't apply here," not
an error — and it's exactly how `build.py` decides whether a signifier is
double-string, with no separate flag anywhere (see `chain.resolve`'s
docstring). An *optional* element that's marked present must resolve, or
it's a real authoring bug (missing relationship or gap coverage) — that's
allowed to raise.

## Whole-character vertical centering

Rather than hanging from one element's fixed default Y and only growing
in one direction as more optional elements are added, every combination's
positions are shifted uniformly so the topmost..bottommost span (per
`vertical_center_order`) is centered on `geometry.CENTER_Y` (500).
`chain.resolve()` computes this per presence-combination — `bare_fy()`
handles the one case with no right-hand glyph at all (currently resolved
against the `"default_jzp"` engine specifically; may need to become
per-topology if a second topology ever needs its own bare-fallback case).
Only the Y axis is recentered — `geometry.CENTER_X` is declared but
currently unread; nothing recenters horizontally today.

## Approximate additive centering (opt-in, per-layout)

The exact centering shift above is computed from the topmost/bottommost
*present* rank's real resolved span -- correct, but combo-sensitive: two
presence-combinations sharing the same backtrack up to some element can
still need different absolute values for it, purely because of what's
present elsewhere in the word (see "Scoping" below, `optional_lookahead`).
That combo-sensitivity is a real driver of this module's rule-count/
subtable-byte cost -- a "chords"-style layout with many optional elements
can overflow the 64KB GPOS lookup ceiling well before its raw rule count
looks alarming (see `estimate_dynamic_pos_bytes`'s docstring).

A `LAYOUTS` entry can opt into a coarser, additive approximation instead,
via a `centering` key:

```json
"vertical_center_order": [["fy"], ["left", "hui"], ["jc"], ["zhu"], ["right"]],
"centering": {
  "mode": "additive",
  "per_rank": [-50, -100, -20, -20, 0]
}
```

`per_rank[i]` is a fixed contribution for `vertical_center_order[i]`,
summed **once** if *any* member of that rank is present and resolved --
not once per present member (`chain._additive_shift`). This matches
`vertical_center_order`'s own semantics: same-rank siblings like
`["left", "hui"]` sit side by side, not stacked, so a second present
member of an already-counted rank shouldn't add further height. A rank
containing only an always-present element (e.g. `default_jzp`'s own
`["right"]`) just becomes a constant baseline -- never combo-sensitive,
safe to set to whatever offset makes the sum line up, or leave at `0`.

Absent `centering` entirely, a layout keeps today's exact
`_centering_bounds` calculation byte-for-byte -- this is opt-in, and every
existing `LAYOUTS` entry is unaffected until it adds this key.

**Why this actually shrinks rule count, not just rounds the numbers**:
on its own, swapping in a coarser value computation changes nothing about
rule count -- `build.py` still needs *some* way to tell combos apart to
pick the right baked-in `<x y>`. The actual saving comes from
`_signifier_rules`'s `optional_lookahead`, which -- only under
`centering_mode == "additive"` -- drops an element from the
disambiguating lookahead if a same-rank sibling is already present
elsewhere in that combo. Since the OR-then-sum model guarantees a second
present sibling can't change the result, that element carries zero
disambiguating value; omitting it makes the generated rule strictly *less
specific* (matches a broader set of real words), which is safe under the
existing most-specific-first sort -- it isn't a special case fontTools
needs to know about, just a shorter, more general rule. The more a
layout's ranks group multiple optional elements together (or the more one
rank's contribution dominates the others, as `chords`' own `chord` glyph
is expected to), the more combos collapse onto the same lookahead
requirement, and the fewer distinct rules get emitted.

**Known limitation**: `bare_fy()` (the one case with no right-hand glyph
at all) computes its own centering shift inline, always via the exact
formula, regardless of `centering_mode` -- it's already hardcoded to
`default_jzp` specifically (see `gen_dynamic_gpos`), so this only matters
if `default_jzp` opts into additive mode; revisit if that combination is
ever actually needed.

## Scoping (the correctness-critical part)

Every rule `build.py` generates for one (topology, signifier, presence-
combination) triple requires that combination's exact backtrack/lookahead
— so it can only ever match a word that actually resolves to that exact
signifier. Concretely, `_signifier_rules` splits the real sequence
(`order`, filtered to this combo) into `before`/`after` the pivot:
elements *before* the pivot chain together with lookahead always ending in
the pivot's own per-signifier class (that's what prevents leaking into
another family's word); elements *after* the pivot (leaves) each
independently attach right after whatever precedes them, scoped via the
pivot's class already sitting in their backtrack.

**The pivot and every leaf also carry a same-family disambiguating
lookahead** (`optional_lookahead`, listing whichever *optional* elements
this specific combo has, in order) — this was **not** true in an earlier
version, which gave the pivot and every leaf *no* lookahead at all on the
theory that "its value never depends on what, if anything, follows." That
theory is wrong whenever `chain.resolve`'s whole-stack vertical-centering
shift (see below) is itself combo-sensitive: the shift is one number
applied uniformly to *every* resolved element, and it depends on which
ranked elements are present *anywhere* in the word — so a leaf (or the
pivot) can need a different absolute value across combos even though its
own presence/backtrack never changes. Without a lookahead to tell those
combos apart, every one of them compiles to a byte-identical FEA rule
(same backtrack, same empty lookahead, different baked-in `<x y>`), and
since `rules.sort`'s specificity-based ordering is a stable sort, only
whichever combo happened to be generated *first* (`itertools.product`'s
enumeration order) ever wins — for *every* real word, regardless of what
it actually contains. Confirmed as a real (not theoretical) bug while
building `chord_left`'s `fy_1`/`fy_2` leaves and the `chord` pivot itself:
`chord` rendered at a fixed height no matter which of `fy_1`/`left`/`hui`/
`jc`/`fy_2` the real word actually had, because its rule had zero
lookahead and thus zero way to prefer the variant matching the real
combo. `optional_lookahead` fixes both the pivot and every leaf the same
way `before`-pivot elements already worked (list whichever later elements
this exact combo has, and let most-specific-first sorting fall through to
a less-specific rule when a real word is missing one of them) — filtered
to *optional* elements only, deliberately excluding non-optional/leaf
areas like `string`: those are attempted in **every** combo regardless of
whether a real word actually has that glyph (`chain.resolve` tolerates
them failing to resolve, see below), so their presence carries zero
combo-distinguishing information, and requiring one in a lookahead would
wrongly reject a real word that genuinely lacks it. The one case this
deliberately still special-cases correctly: a *bare* pivot with nothing
after it at all (e.g. a lone chord glyph, no string) naturally gets an
*empty* `optional_lookahead(after)` for that combo, since `after` itself
is empty — so the original "don't require a leaf to follow the pivot"
guarantee still holds, just as a special case of the general mechanism
rather than a separate hardcoded rule.

Rules are emitted **most-specific-first** (longest backtrack+lookahead),
matching `jzpbuild/gpos.py`'s established first-match-wins ordering
discipline within a lookup.

One deliberate gap remains and is explicitly patched: `area_fy` has a
"nothing precedes area_right at all" root default (needed so bare `fy`
alone still gets centered), and that rule has *no* context requirement at
all — the lowest-specificity rule possible. Left unguarded, it would also
fire (incorrectly) whenever `area_fy` is followed by anything that isn't
one of this module's own longer matches: a `loki`/`nc`/`tiao`/`mo` word,
or a genuine "blank" (no right hand at all) word with fy+hui/left/jc/zhu
— both of which the classic pipeline already positions for real.
`build.py` adds one explicit mid-specificity "blocker" rule: if `area_fy`
is immediately followed by hui/left/jc/zhu or any other family's
right-hand class (`@area_fy_blocker`, built from classic's own shared
per-family classes), zero it out instead. Every genuine rule above
requires its own per-signifier class (disjoint from this blocker class,
and a subset of classic's per-family class) somewhere in its own context,
so it's always at least as specific and never shadowed by the blocker.

Verified against the full `tests/test_shaping.py` corpus (78 cases) with
gou/io/li live: 0 glyph-name mismatches, 0 position differences for every
case outside this module's scope, and correct (though not always
pixel-identical to classic — see "Known simplifications") output for
every gou/io/li case.

## Per-signifier scoping and `signifiers.py`

Classic `jzpbuild/features.py` defines one glyph class per *family*
(`@area_right__gou = [ lg_gou lg_da ]`) — this module additionally
generates one class per *signifier* (`classes.py`:
`@area_right__gou__lg_gou`, `@area_right__gou__lg_da`, separately), which
is what lets `RELATIONSHIPS`' `gap` overrides tune `lg_gou` and `lg_da`
independently instead of forcing them to share one value. `signifiers.py`
provides the ASCII-key ↔ glyph translation this needs, built by scanning
`components.csv` (via `jzpbuild.data.load_components()`, read-only —
plain `jzpbuild` is unaffected regardless) restricted to
`_RELEVANT_AREAS` (`area_right`, `area_chord`) — **not** every row, since
some input keys are genuinely ambiguous across areas (e.g. `"V"`/`"jiu"`/
`"lun"`/`"banlun"` each name two different glyphs depending on whether
they're in `area_right`/`area_hui` or their vertical-mode `area_char`
variant form; GSUB picks the right one from surrounding context, which
this module has no equivalent of — adding an area to `_RELEVANT_AREAS`
needs an explicit check that it doesn't introduce that kind of collision).

Some pivots are glyphs that live entirely outside `components.csv` —
cuo's `blank_bar` (what `|` substitutes to) is one of
`config.CONTROL_GLYPHS`, wired up via a hardcoded rule in classic
`features.py`'s `gen_liga_feature()` (`sub bar by blank_bar;`), not a
`components.csv` row at all. `signifiers.py` has a small supplementary
table (`KEY_TO_GLYPH["|"] = "blank_bar"`) for exactly this case — add an
entry there whenever a new `LAYOUTS` pivot turns out to be one of these
control glyphs.

`classes.signifier_token` builds FEA class names from the **glyph name**,
not the raw key — a real bug hit while adding `chord_right`: `|` isn't a
valid character inside a FEA identifier, so embedding it directly (as an
earlier version of this code did) produced a `FeatureLibError: Unexpected
character: '|'` at compile time. Glyph names in this pipeline are always
identifier-safe; ASCII keys aren't guaranteed to be.

## Gap overrides can key off any area's glyph identity, not just the pivot

Originally, `resolve_gap`/`chain.resolve` took a single `signifier: str` (the
word's technique key) — so a relationship's gap could only ever vary by
*which technique glyph* the word used, never by any other area's own
identity. This was a real limitation: e.g. `jc`↔`hui`'s gap couldn't depend
on which specific `area_hui` glyph (`md_5` vs `md_9` vs...) was actually
present, because `hui`'s specific glyph was never threaded through the
resolver at all — every non-pivot area collapsed to one generic
`@area_{name}` FEA class regardless of which glyph occupied it.

This is now generalized: `chain.resolve` takes `present_glyphs: dict[str,
str]` — {area: glyph} for every area whose specific glyph identity is
pinned down in one specific rule-generation variant of a word (the pivot's
own area -> its own glyph, plus whichever other areas' specific glyphs are
pinned down for that variant). Per relationship, `chain.resolve` looks up
`present_glyphs.get(rel["base"])` and `present_glyphs.get(elem)` and passes
both into `anchors.anchor`/`resolve_gap` as `base_glyph`/`elem_glyph` --
`resolve_gap` then matches a gap-override entry's `base_signifiers` against
`base_glyph` and its `elem_signifiers` against `elem_glyph`, independently
(see the `gap` shape section above). This unifies technique-based overrides
and any-other-area overrides under one mechanism, and additionally supports
a genuine conjunction across both sides in a single entry (something a flat
signifier-set match could never express).

**Efficiency insight (why this doesn't blow up combinatorially):**
`build.py` only branches, per identity-sensitive area, over the **distinct
glyph names actually referenced by that layout's own gap overrides** (via
`identity.area_glyph_buckets`) plus one grouped "every other glyph in this
area" catch-all bucket (`classes.area_glyph_other_token`) — **not** one
rule per literal glyph the area could ever contain (which could be ~20 for
`area_hui`). The explicit-glyph classes and the "other" class are always a
strict partition of the area's full glyph set (disjoint, covering
everything), so there's no FEA rule-ordering ambiguity between them: a real
shaped word matches exactly one, regardless of emission order. (Note that if
all possible glyphs in the area are already explicitly covered by the overrides,
the catch-all 'other' class would be empty. To prevent compiling empty classes,
which `fontTools` rejects with a `FeatureLibError`, the compiler automatically
skips generating the 'other' class and its corresponding rule branches in this case.)

If an area's gap override has **no** catch-all entry, only the explicitly-
listed glyphs get branched — a real word with that area present but
occupied by some other, unlisted glyph will fail to resolve for that
relationship at build time (a `KeyError`, same as any other missing gap
coverage — see "Fully generic dependency-graph resolver" above). This is by
design (an authoring gap to fix, not a silent fallback), same as this
module's existing `string_top`/`string_bottom` catch-all-less overrides.

`selector.contains` (which ASCII keys route a word to a `LAYOUTS` entry at
all) was deliberately **not** converted to glyph names alongside this — it
lives in a different, unambiguous domain (technique keys only, already
1:1 with glyphs via `KEY_TO_GLYPH`, no cross-area collision risk the way
raw `keys`/`latin` values have), and keeping it as short ASCII keys is
significantly more readable for authors and for `tools/jzpbuilder-
dynamic.html`'s UI than the equivalent glyph names would be.

## Visual editor and JSON sidecar

`dynamic_positioning/layouts_data.json` (loaded by `geometry.py`, see
"Structure" above) is editable directly, but the intended workflow is
`tools/jzpbuilder-dynamic.html` (served via `python3 -m
jzpbuild.devserver`, alongside the classic pipeline's `jzpbuilder.html`).
It renders one `LAYOUTS` entry's areas as boxes — positions always computed
by POSTing the in-browser (possibly unsaved) editing state to the
devserver's `/api/dynamic/resolve`, which calls the *real*
`anchors.AnchorEngine`/`chain.resolve`, never a JS reimplementation — and
supports: editing relationships via click-to-select edges (axis-constrained:
left/right edges only pair with left/right, top/bottom only with top/bottom
— **first edge clicked is the `elem`, second is the `base`**, i.e. select
what you're positioning, then what you're positioning it relative to);
dragging to reposition (back-computes the gap) or resize an area (shared
`area_sizes`, so a resize in one layout's view affects every layout that
references that area); per-layout drag-to-reorder + optional/pivot/visibility
controls for `order`; a **leaves** list (below the order list) for areas the
current layout's `relationships` reference but that have no `order` entry at
all — e.g. `string_top`/`string_bottom`, or `chord_left`'s `zhu` — computed
purely by diffing relationship-referenced areas against `order`, nothing in
the JSON marks a leaf explicitly; drag one up into the order list to give it
a real opt/pivot entry, or toggle its preview-only visibility with the eye
icon (doesn't touch `resolve`/the build, purely what `renderCanvas` draws);
a **lock toggle** (🔒/🔓, next to the eye icon, order list and leaves list
both) that adds `pointer-events: none` to that area's canvas box — disables
dragging *and* lets every click (including edge-clicks) pass straight
through to whatever's rendered underneath, for untangling two areas that
visually overlap (`lockedByLayout`, preview-only, never saved); a
**Signifier** section (the pivot area's own dropdown, driving the preview)
whose "add key" control is itself a dropdown sourced from `keyToGlyph`
(the server-derived `signifiers.KEY_TO_GLYPH`) — restricted to keys not
already in this layout's `selector.contains`, rather than a free-text box
that could add a typo'd or already-claimed key with no real glyph behind
it; and a **Relationship panel**, described in its own section below.

Clicking an area opens the Relationship panel for every relationship this
layout declares with that area as `elem` — across every axis and every
candidate `base`, not just whichever one the resolver currently has active.
It reopens the same way from clicking a measurement label on canvas, which
additionally pre-selects that exact relationship.

### The Relationship panel

The panel is split into two independent side-by-side sections, **X axis**
and **Y axis** (an area with declared relationships on only one axis — most
leaves — only shows that one section). Each section is entirely
self-contained: its own tab strip, its own rule editor, its own "matches
rule N of M" status line. Switching the X tab never disturbs the Y
selection or vice versa.

- **Tabs** — one per candidate `base` on that axis (`root`/`fy`/`hui`/`left`
  for `jc`'s Y axis, say), but only the ones actually reachable right now
  are shown: `reachableTabs()` reuses `lastChosen[elem][axis]` — the exact
  same value `findActiveRelationshipsForArea`'s dimension-line drawing
  already keys off, not a JS re-derivation of chain.py's tie-break rules —
  so only the literal base the resolver picked gets a tab; a
  root/lower-priority candidate that's currently shadowed doesn't appear
  (its rule set is still editable, just not surfaced as a tab, until it
  becomes the actual winner). Re-opening the panel for the *same* area (a
  drag's trailing click included — see below) leaves each axis's selected
  tab alone; only switching to a different area, or clicking a specific
  measurement label, changes the selection.
- **Header line** — `base: X's edge → element: Y's edge` — is plain
  text/labels, not editable controls. Creating or retargeting a
  relationship is deliberately the canvas's job (drag an area, or
  click-to-select two edges — see above); this panel is for
  inspecting/tuning a relationship that already exists (its gap rules) and
  removing it, via the `×` button at the end of the line
  (`deleteRelationship`) — the one thing neither drag nor edge-clicking can
  do (both only ever add or retarget a candidate). Deleting rolls back and
  alerts if the layout can no longer resolve without it (same safety net
  as edge-click's own cyclic-dependency check), rather than silently
  leaving a broken canvas.
- **Rules** render as `if [base chip(s)] and [elem chip(s)] then gap is [ ]`
  — the closed chip box shows the actual selected glyphs' icons (or
  `(any)` when that side is unconstrained); clicking it opens a checkbox
  list to edit the rule's condition. A trailing bucket with neither side
  constrained renders instead as `for all other cases, gap is: [ ]` — this
  row is optional (`+ add catch-all (else)`) and removable, since some
  relationships (`string_top`/`string_bottom`) intentionally have no
  catch-all. `+ add rule` always inserts before a trailing catch-all, never
  after (first-match-wins would make a rule appended after one unreachable).
  **Exception**: when a relationship's gap is the common case — one
  unconditional value, no glyph-identity rules at all (exactly one
  catch-all bucket) — its editor renders *inline* on the header line itself
  (`... is [value] unless... ACTIVE`) instead of as a separate one-row list
  below, so the ordinary no-conditions relationship reads as one line, not
  two. Clicking `unless...` there does the same thing `+ add rule` does
  (`addConditionalRule`, shared by both) — turns it into a real
  glyph-conditioned rule set, at which point the full row-list rendering
  (and a gap-free header line) takes back over on the next render.
- **Preview / "active rule" highlighting** — whichever rule the *current*
  preview glyphs actually resolve to (mirroring `anchors.resolve_gap`
  exactly, computed in JS by `activeBucketIndex`) is outlined and badged
  `ACTIVE`, with a status line underneath (`matches rule 2 of 4 → gap
  -400`, or an explicit "no rule matches" for a leaf-style relationship
  with no catch-all). **Clicking a rule row pins a matching glyph combo for
  both sides**, making it the active one so its gap is immediately visible
  on canvas — no more hunting down which chips to click by hand. Clicking
  the same row again cycles to the *next* combo in that rule's base×elem
  cross product (`comboAt`) rather than re-picking randomly, so repeated
  clicks walk every legal combination on purpose. Clicking the catch-all
  row does the equivalent for it specifically (`previewCatchAll`): since a
  rule can be dodged through either side alone (an unconstrained side can
  never be dodged), it brute-forces the base×elem cross product against
  every earlier rule and cycles only through combos that actually reach
  the catch-all — a no-op if every combo is already claimed above it.
- There's no separate "preview as" selector anymore — clicking a glyph
  chip directly *is* the preview control, for any area (pivot or not).

### Single glyph-identity source of truth (`assign`)

Every area's "what glyph is this right now" — for canvas rendering *and*
for gap-rule matching *and* for what's sent to `/api/dynamic/resolve` as
`area_glyphs` — is `assign` (the same dict the bottom candidate-list picker
writes) for every non-pivot area, and additionally kept in sync with the
Signifier dropdown's `signifierByLayout` for the pivot area specifically
(`glyphForArea`/`pinGlyph`). This used to be two separate dicts
(`assign` for rendering, a since-removed `areaGlyphByLayout` for matching)
that could silently diverge — e.g. the bottom candidate list would update
what's drawn without updating what the gap math keyed on, so a rule could
look "active" while the canvas showed a different gap, or vice versa. Every
code path that can set an area's glyph (candidate-list clicks, rule-row
chip clicks, "Test random components", the Signifier dropdown) now goes
through the same sync point, pivot included.

`fillCurrentLayoutRandom` ("Test random components") and the bottom
candidate list both source from `legalCandidatesForArea`, not raw
`csvCandidatesForArea` — for the **pivot** area, `components.csv`'s
`area_right`/`area_chord` column is shared across every layout with that
kind of pivot, so an unrestricted pick could land on a technique glyph
that belongs to a *different* layout entirely (e.g. `lg_fanqi` showing up
as a "legal" `default_jzp` `right` candidate). `legalCandidatesForArea`
intersects with the current layout's own `selector.contains` for the
pivot; every other area is unaffected. `relSignifierCandidatesForArea`
(the rule-editor chip source) goes through the same restriction.

`/api/dynamic/resolve` requests aren't cancelled or sequenced — any editor
action that changes preview state fires a fresh overlapping `fetch`, and
nothing stopped an older, still-in-flight request's response from landing
*after* a newer one's and silently overwriting `lastResolved` with stale
data (visible as: the Relationship panel's status line shows the right
number, but the canvas boxes don't reflect it). `resolveAndRender` now
tags each call with a monotonic `resolveSeq` and discards a response if a
newer call has since started.

### Interactive Dimension Lines & Real-Time Updates
* **Selected Element Dimension Lines:** Selecting an element shows red dimension lines (`stroke="#d93838"`) for all active relationships connecting to it (as either `elem` or `base`). 
* **Margin Positioning & Staggering:** Dimension lines are drawn outside the white frame boundary (X-axis measurements sit at the bottom; Y-axis measurements sit to the left in the gray wrap area). If the selected element has multiple active relationships on the same axis, the lines are staggered sequentially (offset by `40px` per step) to stay side-by-side.
* **Overlap Protection:** When adjacent labels are too close (such as when the gap distance is `0`), a collision resolver shifts the base name, element name, and gap value tags vertically/horizontally to ensure they never overlap or run together.
* **Real-time Drag updates:** Dragging an area to reposition it computes the relative gap values and updates the model dynamically, redrawing the red dimension lines and numbers — and, if the Relationship panel is open on the relationship being dragged, its `gap:` input — in real time as you drag, not just on mouseup.
* **Visibility-aware constraints:** Toggling an optional element off/on (using the eye icons in the order panel) recalculates active relationships based on the resolver's actual execution path (`lastChosen`), updating the shown dimension lines dynamically (e.g. linking `E` directly to `A` if `B, C, D` are hidden, or linking `E` to `D` when they are visible). The Relationship panel's tab visibility (above) reuses this exact same `lastChosen` data, so a tab and its dimension line agree on what's currently reachable by construction.

## cuo: current status (incomplete, read before relying on it)

`chord_left` (`C`/`DC`/`FC`/`TT`) and `chord_right` (`|`) are early,
minimal `LAYOUTS` entries — real progress toward covering cuo, but not
there yet:

- **Neither has `fy`/`left`/`hui` yet.** Classic `cuo_rules()` (in
  `jzpbuild/gpos.py`) supports those on both segments; these entries
  currently only model `chord`/`bar` → (optionally `jc`) → `string`.
  Real cuo words that exercise the missing areas will fall through
  unpositioned by this module.
- **`AREA_SIZES["chord"]`/`["bar"]` are rough placeholders**
  (`chord`: 1000×1000, `bar`: 500×1000) invented for this module, not
  derived from real glyph outlines — and note `bar`'s *width* here isn't
  actually load-bearing for `|`'s own x-placement (`centered_x_left_border()`
  returns the constant `CENTER_X` regardless of `AREA_SIZES`), so retuning
  it alone won't change anything visually. The real increment after typing
  `|` is `blank_bar`'s glyph advance width (`config.CONTROL_GLYPHS`,
  1000 units as of this writing) — a base-glyph metric shared with every
  pipeline, not something this module's `pos` rules touch at all (`build.py`'s
  `_Rule.render` always emits a `0 0` xAdvance/yAdvance component).
- **Double-counting risk under plain `--dynamic_pos`.** Classic
  `gpos.py::cuo_rules()` has no zero/skip mechanism analogous to the one
  `li` needed (see below) — its blocks are only zeroed under
  `--dynamic_pos_only`'s blanket `zero_others`, never under plain
  `--dynamic_pos`. If `chord_left`/`chord_right` ever produce real
  (non-zero) positioning under plain `--dynamic_pos`, it will double-stack
  with classic's own un-zeroed cuo positioning — the exact bug class this
  module's whole design (see "Why not mark attachment") exists to avoid.
  **Test cuo exclusively under `--dynamic_pos_only` until this is fixed.**
- The `chord`/`bar` pivot sits *first* in `order` (`{"pivot": True}` at
  index 0), unlike `default_jzp`'s pivot (last) — confirmed against
  classic `cuo_rules()`, where the chord/bar anchor precedes left/hui in
  the glyph sequence. This is exactly the kind of case the `order`-based
  design (rather than an assumption baked into `build.py`'s code) exists
  to support — an earlier version of `build.py` hardcoded "pivot always
  comes last," which silently produced wrong backtrack/lookahead for a
  pivot-first topology like this one.
- **Fixed**: classic `jzpbuild/gpos.py::gen_gpos()`'s "blank" (no
  right-hand technique at all) fallback rules — `layout_blank`/
  `layout_blank2`/`layout_blank3`, meant for a bare harmonic marker
  (`fy` + `left`/`hui`, nothing else) — were **never zeroed** under
  `--dynamic_pos_only`: their three `emit_block` calls simply didn't pass
  `zero=zero_others` (every other `emit_block` call in the file does).
  This never mattered for `gou`/`io`/`li` since a real right-hand-family
  word always matches classic's own, more-specific, family-requiring rule
  instead — but `chord_left`'s pivot (`xl_cuo`/`xl_tt`) isn't a member of
  any `@area_right__{family}` class, so nothing in the "blank" rules'
  own backtrack/lookahead excludes a cuo word from matching them too.
  Result: a real word like `Cfys5` (chord + `fy` + `left` + `hui`) landed
  `mod_fanyin` at the **sum** of classic's unzeroed `(290, 698)` and
  `dynamic_pos`'s own `(290, 741)` — `(580, 1439)` — since GPOS
  single-adjustment values from separate lookups accumulate (the exact
  failure class "Why not GPOS mark attachment" above exists to avoid,
  reached this time through a different, previously-unnoticed gap). Now
  fixed: all four `emit_block` calls under "blanks (no right hand)" pass
  `zero=zero_others` like everything else in the file. Worth remembering
  if `zero_others`-style zeroing is ever extended elsewhere: **any**
  classic fallback whose own match conditions don't explicitly exclude a
  new pivot family is a candidate for this same double-counting bug the
  moment that family's dynamic-positioning rule goes non-zero.

## Rule-count scaling (measured, not estimated)

Per-signifier generation means `gou`/`io` now generate roughly double what
a per-family version would (2 signifiers each vs. 1 rule set per family).
Re-measure from the generated `.fea` if you need current exact counts —
the shape of the scaling argument is unchanged from before:

- **More right-hand families** (bringing `loki`/`nc`/`tiao`/`mo` into this
  module): *linear* in family/signifier count.
- **More independently-optional stacking elements** (a slot beyond
  fy/left/hui/jc/zhu): *exponential* — the presence-combination space is
  2^(number of optional elements) per signifier. This is the real cost
  driver, not family count — worth deciding how many more optional slots
  a topology's `order` will realistically need before extending further.

  `right`-attaches-to-`jc`) — missing this raises `KeyError` the first

## Adding a custom signifier

A *signifier* is one ASCII key in some `LAYOUTS` entry's `selector.contains`
— the finest-grained unit this module positions (`signifiers.py`, see
"Structure" above). There are two genuinely different cases, depending on
whether the key's glyph is a real designed shape or an invisible mode-
trigger glyph:

**Case 1 — the glyph is a real `components.csv` row (has an SVG).** Most
signifiers are this case (`k`→`lg_gou`, `l`→`lg_da`, ...). Nothing to add
in `dynamic_positioning/` itself:

1. The row must already exist in `components.csv` with a non-empty `latin`
   column, and must belong to one of `signifiers._RELEVANT_AREAS`
   (`area_right`, `area_chord`, `area_left`, `area_char` as of this
   writing). `signifiers.KEY_TO_GLYPH` picks it up automatically — no
   registration needed there.
2. If the row's area isn't in `_RELEVANT_AREAS` yet, adding it is *not*
   always safe — check for a cross-area key collision first (same
   diligence as the `"V"`/`"jiu"`/`"lun"`/`"banlun"` case in
   `signifiers.py`'s docstring): does this key's `latin` value already
   name a *different* glyph in some other area? If yes, `_RELEVANT_AREAS`'
   ordering decides which one wins (earlier-listed area wins, see
   `signifiers.py`), which may not be what you want.
3. Reference the key in a `LAYOUTS` entry's `selector.contains` (an
   existing entry, if it's just a new signifier within an existing family/
   topology, or a new entry per "Adding another family" /
   "Adding a genuinely new topology" below).

**Case 2 — the glyph is an invisible control glyph, not a designed shape**
(mode triggers/separators like `|` for cuo or `:` for vert-mode — see next
section for how `:` was added). These deliberately have **no**
`components.csv` row and **no** SVG — they're not something a user ever
sees standing alone, just a signal GSUB substitutes on the way to
triggering a different layout. Steps:

1. Confirm (or add) the glyph in `config.CONTROL_GLYPHS` (name →
   `(codepoint, advance_width)`), e.g. `"blank_colon": (0x58003, 1000)`.
   This is what actually reserves the glyph in the font — `base.py`
   generates it directly from this table, no SVG/`glyphs.py` pipeline
   involved at all.
2. Confirm (or add) the GSUB rule in `jzpbuild/features.py` that
   substitutes the raw typed character to that control glyph, e.g. `sub
   colon by blank_colon;` (`gen_liga_feature`/`gen_c2j_char_symbols`). If
   the character has a fullwidth Chinese-input counterpart (e.g. `：` for
   `:`), check whether `gen_c2j_char_symbols` already normalizes it to the
   ASCII form upstream (it does for `,`/`(`/`)`/`:`/`|` today) — if so, you
   only need the ASCII entry; the fullwidth one collapses into it for free
   and needs no separate signifier.
3. Add the key to `signifiers.py`'s supplementary `KEY_TO_GLYPH` table
   (next to the existing `"|"`/`":"` entries), mapping the raw typed
   character to the *final* substituted glyph name (`blank_colon`, not
   `colon`) — this is the one manual registration step this case needs,
   since `KEY_TO_GLYPH`'s automatic scan only ever sees `components.csv`
   rows.
4. Reference the key in a `LAYOUTS` entry's `selector.contains`, same as
   case 1.

Either way, `classes.signifier_token` builds FEA class names from the
**glyph name**, never the raw key — matters if your key isn't
identifier-safe in FEA syntax (`|` isn't; see "Per-signifier scoping and
`signifiers.py`" above for the bug this caused once already).

## Worked example: adding `:` for vert-mode

This is exactly how the `:` signifier and its `vert` topology were added,
as a concrete walkthrough of "Case 2" above plus "Adding a genuinely new
topology" below:

1. `blank_colon` already existed in `config.CONTROL_GLYPHS`, and `colon`
   already substituted to it in classic `features.py` (vert-mode already
   existed in the classic pipeline, being ported here) — so step 1/2 above
   were already done; only `signifiers.py` needed the addition:
   `KEY_TO_GLYPH[":"] = "blank_colon"`, with a comment noting the fullwidth
   `：` collapses into plain `:` upstream via `gen_c2j_char_symbols`, so it
   needs no separate entry.
2. A new `LAYOUTS` entry named `"vert"` was appended to
   `layouts_data.json` (or a sidecar file loaded via `--positions`, for
   staging before merging into the real file — see "Visual editor and JSON
   sidecar" above; note `tools/jzpbuilder-dynamic.html`/the devserver only
   ever read `config.DYNAMIC_LAYOUTS_JSON`, so a sidecar file isn't visible
   to the editor until it's merged in or the config path is repointed),
   `selector.contains: [":"]`, everything else left empty for
   `jzpbuilder-dynamic.html` to build out interactively.
3. **Pitfall hit doing this**: the pivot area's `order` entry must have
   `"optional": false` — the pivot is the signifier's own glyph, so it's
   always present by definition (see `chord_right`'s `bar` entry for the
   reference example). Marking it `"optional": true` passes silently at
   `AnchorEngine.__init__` (only the *count* of `pivot: true` entries is
   checked there, not whether that entry is also optional) but crashes
   later in `build.py._signifier_rules` — `seq.index(engine.pivot)` raises
   `ValueError` the moment `build.py` enumerates a presence-combination
   that happens to omit it.
4. Test with `python3 -m jzpbuild --dynamic_pos_only --positions
   path/to/vert-layout.json -o /tmp/test.ttf` — `--dynamic_pos_only` so a
   still-incomplete `vert` topology fails visibly instead of silently
   falling back to classic's own (still-present, untouched) vert-mode
   rules.

## Repeated-slot areas (`char_1`, `char_2`, `fy_1`, `fy_2`, ...)

Some topologies need the *same* underlying glyph set to appear more than
once in one word — vert-mode's stacked rows (`char_1`, `char_2`, ... for
successive `area_char` glyphs), or `chord_left`'s two `fy` markers
(`fy_1`/`fy_2`, one per cuo segment). This module resolves such a "repeat
slot" area's real glyph membership itself, fully independent of classic —
no per-number registration needed beyond just using the area in
`LAYOUTS`:

- `signifiers.csv_column_for(area)` resolves any area name to its real
  `components.csv` column, falling back to stripping a trailing `_N`
  (`"char_2"` → `"char"`) and re-checking if `area` itself isn't
  registered — so any area whose *base* name (`"char"`, `"fy"`, `"left"`,
  ...) already has a real column is automatically treated as another slot
  of it, with **no cap** on how many numbered slots a topology can invent.
  `identity.area_glyphs` was generalized to use this too (previously a
  direct `AREA_TO_CSV_COLUMN[area]` lookup, which only worked for exact,
  pre-registered names).
- `classes.gen_repeated_area_classes()` scans every `LAYOUTS` entry for
  non-pivot areas that aren't one of classic's own pre-declared base
  classes (`classes._CLASSIC_BASE_AREAS`, essentially
  `signifiers.AREA_TO_CSV_COLUMN`'s keys) and generates a class for each,
  straight from `identity.area_glyphs()` — named `@dp_area_{area}`
  (`classes.repeated_area_token`), **not** `@area_{area}`. `build.py`'s
  generic `token()` picks between the two: `@area_{area}` for anything in
  `_CLASSIC_BASE_AREAS` (reuse classic's real, already-declared class),
  `repeated_area_token(area)` otherwise (self-generated).

**Why the separate `@dp_area_` namespace, not just `@area_{area}` for
everything:** classic `jzpbuild/features.py::gen_classes()` already
declares its *own* row-numbered vert-mode aliases for an unrelated purpose
(`@area_char1`/`@area_char2`.../`@area_left_1`/`@area_hui_1`... up to a
hardcoded 4, all identical-membership copies of `@area_char`/`@area_left`/
`@area_hui`) — under an inconsistent convention this module doesn't
follow (`char{i}` has no underscore, `left_{i}`/`hui_{i}` do). A real bug
was hit taking the shortcut of reusing classic's exact names: `left_1`
happens to collide by pure coincidence with one of classic's own aliases,
and fontTools' `feaLib` `SymbolTable.define` is a plain dict write with
**no duplicate-definition error** — a later `@name = [...]` silently
overwrites an earlier one. Reusing classic's namespace only "worked" as
long as both definitions' membership happened to match; the distinct
`@dp_area_` prefix makes that whole class of bug structurally impossible
instead of coincidentally avoided, and this module now never depends on
classic's hardcoded cap of 4 or its naming quirk at all.

## Adding a genuinely new topology

Append a new `LAYOUTS` entry with its own `areas`/`vertical_center_order`/
`relationships`/`order`/`selector` — `build.py`, `classes.py`, and
`anchors.AnchorEngine` are all already driven by `geometry.LAYOUTS`
directly, so a new entry is picked up automatically, no separate
registration anywhere else. See `chord_left`/`chord_right` above for a
real (if incomplete) example, and "cuo: current status" for what's still
missing before a cuo-shaped topology is actually correct.

## Known simplifications (not pixel-perfect, by design)

- Most `RELATIONSHIPS` gap values are explicit placeholders this round
  (see geometry.py's module docstring) — expect retuning.
- `area_zhu`'s attachment to `area_right` and li's `string_top`/
  `string_bottom` gaps are two of the few real numbers actually derived
  from matching classic output; most others are not yet.
- Confirmed **algebraically** (not just empirically) for li: no single
  gap value on the `right`-attaches-to-`hui`/`left` relationship can make
  *both* `area_hui`/`area_left` and `area_right` match classic
  simultaneously for a left+hui+li combo — the whole-stack centering
  shift that would satisfy one is mathematically incompatible with the
  one that satisfies the other. Chose to match `area_right` (the
  technique glyph, most visually load-bearing) and let `area_hui`/
  `area_left` drift in that specific combo.
- Per-area box sizes (`geometry.AREA_SIZES`) are generic constants, not
  derived from real glyph outline bounding boxes (cuo's `chord`/`bar` in
  particular — see "cuo: current status").
- `elem_edge`/`base_edge` default to "elem's far edge, base's near edge"
  (e.g. "elem's top touches base's bottom plus gap") for every
  relationship unless written out explicitly — this covers the vast
  majority of real relationships; the exceptions so far are rare enough
  that they're called out inline in `RELATIONSHIPS` where they occur.
- This module's rule count is not dramatically smaller than the classic
  per-layout enumeration it replaces — the authoring win is in
  `geometry.py`'s declarative table (edit a handful of relationships) vs.
  hand-tuning dozens of Figma layout frames, not raw `.fea` line count.

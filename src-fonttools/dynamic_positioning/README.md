# dynamic_positioning — geometry-derived GPOS for right-hand-technique words

**Status: experimental prototype, not the final design.** Fully covers
`gou` (`lg_gou`/`lg_da`), `io` (`lg_ti`/`lg_zhai`), and `li` (`lg_li`) —
replacing `layout_gou/gou2/gou3`, `layout_io/io2/io3`, and
`layout_li/li2/li3` with literal `pos` rules generated from a declarative
table (`geometry.py`) instead of hand-tuned Figma layout frames. Also has
an early, incomplete start on `cuo` (撮 chords: `chord_left`/`chord_right`
in `geometry.LAYOUTS`, keyed on `C`/`DC`/`FC`/`TT`/`|`) — see "cuo: current
status" below before relying on it. All other layout families (`loki`,
`nc`, `tiao`, `mo`, vertical-mode `:` words) are untouched and still
generated by `jzpbuild/gpos.py::gen_gpos()`.

Opt in with `python3 -m jzpbuild --dynamic_pos`. There's also
`--dynamic_pos_only`, which additionally zeroes out every classic-
positioned shape this module *doesn't* cover (other right-hand families,
vertical-mode words, cuo chords) so they render visibly broken instead of
silently working via classic — useful for checking this module's actual
coverage without classic quietly filling the gaps. Both flags are plumbed
through `jzpbuild/genfea.py` → `jzpbuild/gpos.py` (`gen_gpos`'s
`skip_right_keys`/`zero_others` params) and are fully reversible: nothing
in `dynamic_positioning/` is imported unless one of these flags is passed,
and neither flag touches `jzpbuild/features.py` (GSUB) at all — plain
`jzpbuild` is unaffected regardless of anything in this directory.

## Why not GPOS mark attachment (an earlier version of this used it)

The first version of this prototype used GPOS mark-to-base/mark-to-mark
anchors (types 4/6): `area_fy` as a base, `area_hui`/`area_left`/`area_jc`/
`area_zhu`/`area_right` chained on as marks, so an absent element simply
didn't attach — no separate layout needed per jc/hui presence.

That broke as soon as it was tested against a non-gou/io word. `fy`, `hui`,
`left`, `jc`, `zhu` are the *same shared glyphs* across every right-hand
family, not gou/io-specific variants — so the mark rules fired (and
additively stacked on top of) the classic pipeline's own positioning for
`loki`/`nc`/`tiao`/`mo`/`li` words too, since GPOS single-adjustment value
records accumulate across lookups. Confirmed empirically: `fylo3` (fy +
loki + string) rendered `mod_fanyin` at roughly double its correct offset.
Mark attachment has no way to require "and only within a gou/io word" —
anchors fire wherever the glyph shapes match, full stop.

Literal contextual single-adjustment rules (GPOS type 1, chained context)
*can* require an exact backtrack/lookahead sequence, including a specific
per-signifier class (see "Scoping" below) — the same mechanism
`jzpbuild/gpos.py::word_layout_rules()` already relies on for correctness
(every rule it emits, including `fy'` ones, ends with the right-hand
family's own class as trailing context). So this module generates the
same *kind* of rule classic does, just computed from `geometry.py`'s
declarative data instead of authored per Figma layout.

## Structure

- `geometry.py` — pure data. `RELATIONSHIPS`: the spatial-adjacency graph
  for the standard fy/left/hui/jc/zhu/right/string shape (one entry per
  geometric constraint). `AREA_SIZES`: per-area box sizes. `LAYOUTS`: one
  entry per distinct *topology* (see below) — this is what `build.py`
  actually iterates to generate rules.
- `signifiers.py` — ASCII-key ↔ glyph mapping, derived from
  `components.csv` (read-only, via `jzpbuild.data`) plus a small
  supplementary table for glyphs that live outside `components.csv`
  entirely (control glyphs like `blank_bar`). The finest-grained unit this
  module addresses — one step below `config.RIGHT_SELECTORS`' families
  (e.g. `gou` → `k` for `lg_gou`, `l` for `lg_da`, independently).
- `anchors.py` — `AnchorEngine`: a generic engine that resolves one
  `LAYOUTS` entry's relationships into coordinates. One instance per
  entry (see `build.py`'s `_ENGINES`). No hardcoded area names or
  per-pair formulas anywhere in this file.
- `chain.py` — resolves one word combination through one `AnchorEngine`:
  a genuinely generic dependency-graph walk (not a fixed sequential
  chain — see "Three orderings" below), then applies a whole-stack
  **vertical centering shift** (see below) so the composed character is
  centered on `geometry.CENTER_Y` regardless of which optional elements
  are present.
- `classes.py` — generates one FEA glyph class per (family, key)
  signifier (e.g. `@area_right__gou__lg_gou` vs `@area_right__gou__lg_da`),
  separate from `jzpbuild/features.py`'s shared per-*family* classes.
- `build.py` — drives everything off `geometry.LAYOUTS`: for each entry,
  for each key in its `selector.contains`, enumerates every optional-
  element presence-combination, generates one literal `pos` rule per
  (combination, positioned element) pair with the value computed by
  `chain.py`, sorts most-specific-first, and adds the explicit "blocker"
  rule that keeps `area_fy`'s positioning from leaking into words this
  module doesn't cover.

## `geometry.LAYOUTS`: one entry per topology

A *topology* is a distinct spatial-adjacency shape. `gou`/`io`/`li` all
share one (`"default_jzp"`) — they're differently-proportioned
*signifiers* within the same fy/left/hui/jc/right/zhu/string shape, not
different shapes. A genuinely different shape (no `area_right`-equivalent
pivot at all, or a repeated structure) needs its own `LAYOUTS` entry.
Shape of one entry:

```python
{
    "name": "default_jzp",
    "selector": {"contains": ["k", "l", "i", "o", "U"]},   # ASCII keys, see signifiers.py
    "areas": AREA_SIZES,                                    # per-area (w, h)
    "vertical_center_order": [["fy"], ["left", "hui"], ["jc"], ["zhu"], ["right"]],
    "relationships": RELATIONSHIPS,
    "order": [
        {"area": "fy", "optional": True},
        {"area": "left", "optional": True},
        {"area": "hui", "optional": True},
        {"area": "jc", "optional": True},
        {"area": "zhu", "optional": True},
        {"area": "right", "optional": False, "pivot": True},
        {"area": "string", "optional": False},
    ],
}
```

- **`selector.contains`** — which ASCII keys route to this topology.
  `build.py`'s `_engine_for_key` is the *only* place that reads this;
  everything downstream only ever sees whichever single `AnchorEngine` it
  was built for. (There's no `"startsWith"`-style prefix selector kind
  implemented yet — cuo/vertical-mode's real dispatch is a leading
  character, not glyph presence, but `chord_left`/`chord_right` below are
  wired in today via ordinary `contains` on their pivot's own key, not a
  true prefix match. Revisit if/when this actually matters.)
- **`relationships`** — the spatial-adjacency graph (`RELATIONSHIPS`'
  shape, see below).
- **`vertical_center_order`** — visual top-to-bottom *rank* order, used
  **only** for the whole-stack Y-axis centering shift. Same-rank groups
  (`["left", "hui"]`) sit side by side; either may define that rank's box.
  Not the same as `order` (below) or `relationships`' own dependency
  structure — a genuinely different fact (which elements share a row on
  screen), and the three orderings aren't guaranteed to agree, even
  though they do for `default_jzp`.
- **`order`** — the real typed/glyph-sequence fact: which elements are
  optional (drives `build.py`'s presence-combination enumeration and
  backtrack/lookahead construction) and their real sequence position.
  Flat, no sibling grouping needed — typing is inherently sequential (you
  can't type `left` and `hui` "at the same time"), and classic
  `gpos.py`'s own `_lh_combos()` confirms `left` always precedes `hui`
  when both are present, so there's no "either order" ambiguity to model
  here (unlike `vertical_center_order`, which is genuinely about visual
  rows, not typed order). `"optional": False` marks elements that are
  always resolved regardless of whether a given word actually has one —
  nothing later in the sequence needs to condition on a pure leaf's
  presence, and GPOS's own glyph-class matching already handles "did this
  glyph actually show up here" for free (see "Three orderings" below).
  `"pivot": True` marks the **one** always-present element whose glyph
  *is* the signifier itself (`right` for `default_jzp`, `chord`/`bar` for
  cuo) — gets `classes.signifier_token(...)` instead of the generic
  `"@area_{elem}"` token every other element uses. `AnchorEngine.__init__`
  raises if an entry's `order` doesn't mark exactly one pivot.

`RELATIONSHIPS` entry shape:

```python
{"axis": "x"|"y", "elem": <area>, "base": <area>|None,
 "base_edge": <edge>|omitted, "elem_edge": <edge>|omitted, "gap": Gap}
```

For `axis="y"`, edges are `"top"`/`"bottom"` (`base_edge` default
`"bottom"`, `elem_edge` default `"top"`). For `axis="x"`, edges are
`"left"`/`"right"` (`base_edge` default `"left"`, `elem_edge` default
`"right"`). `elem`'s `elem_edge` is placed at `base`'s `base_edge`
position plus `gap` (both expressed in `base`'s own local coordinates,
its own origin at its near corner). Both edge fields are almost always
left at their default — write them out explicitly only when a
relationship genuinely needs the other edge (`anchors.py::anchor()`).
`base=None` means "no dependency" — `gap` is then the literal absolute
default value directly, not a relative offset.

`gap` shape: a plain number (same for every signifier), or an ordered
list of `{"signifiers": [<key>, ...], "value": <number>}` overrides, with
an optional trailing entry that omits `"signifiers"` as a catch-all. A
specific signifier match always wins over the catch-all, regardless of
declaration order (`anchors.resolve_gap`). **`"signifier"` is an ASCII
key** (`"k"`, `"l"`, `"U"`, ...) from `signifiers.py`, not a glyph name —
this is what lets `lg_gou` (`"k"`) and `lg_da` (`"l"`) get
independently-tuned values instead of being forced to share one, unlike
classic's own per-*family* (not per-glyph) granularity.

Most numeric gap values in `RELATIONSHIPS` are placeholders (an explicit
decision to prioritize getting the engine's shape right over re-deriving
exact classic-matching numbers this round) — expect to retune them
against `tests/test_shaping.py` and `font_tester.html`.

## Three separate orderings (don't conflate them)

This module tracks three genuinely independent facts about the same
handful of areas, and an earlier version of it conflated the first two,
which was a real bug (see "Fully generic `chain.py`" below):

1. **Typed/glyph-sequence order** (`LAYOUTS` entry's `order` field) — a
   fact about the input/shaped text. Used by `build.py` to build correct
   backtrack/lookahead context, and nowhere else.
2. **Attachment/dependency order** (`RELATIONSHIPS`' own `base` pointers)
   — a pure geometry/authoring choice: which element's *position* is
   computed relative to which other element's. `chain.py` resolves this
   as a dependency graph, not a walk over (1).
3. **Centering rank order** (`vertical_center_order`) — which elements
   share a visual row, for the whole-stack recentering shift only.

For `default_jzp` these three happen to mostly agree (fy → left/hui → jc
→ zhu → right, typed in that order, each one attaching to whichever
optional predecessor came before it, stacked in that same visual order)
— but they don't have to, and `area_zhu` is the clearest example that
they don't: it's typed *before* `area_right` (fact 1), but its *position*
(fact 2) is computed as a pure offset from `area_right`'s already-resolved
position — a deliberate reversal from an earlier version of this module,
where `zhu` instead attached to whichever of jc/hui/left/fy preceded it.
Visually `zhu` sits right up against the technique glyph, so anchoring it
there (once the technique glyph's position is known) is a better match
for what it's actually doing. This only works because "typed order" and
"attachment order" are tracked separately — flipping the dependency
direction for one element while its glyph-sequence position stays fixed
would be impossible if the two facts were the same field.

## Fully generic dependency-graph resolver (`chain.py`)

No hardcoded element names anywhere in `chain.py`/`anchors.py`. Given a
word's presence flags (from `order`'s optional elements) plus every
always-present element a topology's `relationships` declare,
`chain._choose_relationships` picks, per element per axis, which
candidate relationship applies — preferring (most to least specific): a
candidate whose base is a *ranked* (optional, per `order`) element that's
actually present, highest-rank (most recently typed) first; then a
candidate whose base is a guaranteed-resolvable always-present element;
then the root (`base=None`) default as a last resort. This reconstructs
"attach to whichever optional element was typed most recently" without a
fixed sequential walk, and correctly falls back to the true typed-order
recency rule when multiple ranked candidates are simultaneously present
(e.g. `jc` attaching to `hui` rather than `fy` when both precede it,
because `hui` is ranked later in `order`).

One real bug found and fixed while building this: naively picking "the
first candidate whose base qualifies" in raw declaration order breaks,
because root (`base=None`) defaults are conventionally declared *before*
their overrides in `RELATIONSHIPS` — so that approach picked root every
time, silently ignoring presence entirely. Fixed by ranking candidates by
specificity rather than declaration order.

`resolve()` then walks the (now unambiguous) dependency graph to
completion — resolving whatever has no unresolved dependency first —
rather than assuming any fixed pass order, which is what actually makes
this generic across topologies with different shapes (`default_jzp`'s
fy→...→right→string chain vs. `chord_left`'s much shorter chord→jc→string
chain).

An always-present (non-optional) element is allowed to fail to resolve
for a given signifier — e.g. `string_top`/`string_bottom` have no
catch-all gap, so `KeyError` is *expected* for every signifier but `"U"`
(li). That's silently treated as "this element doesn't apply here," not
an error — and it's exactly how `build.py` decides whether a signifier is
double-string, with no separate flag anywhere (see `chain.resolve`'s
docstring). An *optional* element that's marked present must resolve, or
it's a real authoring bug (missing relationship or gap coverage) — that's
allowed to raise.

## Whole-character vertical centering

Rather than hanging from one element's fixed default Y and only growing
in one direction as more optional elements are added, every combination's
positions are shifted uniformly so the topmost..bottommost span (per
`vertical_center_order`) is centered on `geometry.CENTER_Y` (500).
`chain.resolve()` computes this per presence-combination — `bare_fy()`
handles the one case with no right-hand glyph at all (currently resolved
against the `"default_jzp"` engine specifically; may need to become
per-topology if a second topology ever needs its own bare-fallback case).
Only the Y axis is recentered — `geometry.CENTER_X` is declared but
currently unread; nothing recenters horizontally today.

## Scoping (the correctness-critical part)

Every rule `build.py` generates for one (topology, signifier, presence-
combination) triple requires that combination's exact backtrack/lookahead
— so it can only ever match a word that actually resolves to that exact
signifier. Concretely, `_signifier_rules` splits the real sequence
(`order`, filtered to this combo) into `before`/`after` the pivot:
elements *before* the pivot chain together with lookahead always ending in
the pivot's own per-signifier class (that's what prevents leaking into
another family's word); the pivot's own rule has *no* lookahead
requirement (its value never depends on what, if anything, follows — the
first version of this fix wrongly required a leaf to immediately follow
the pivot, which broke the valid "bare pivot, nothing after" case, e.g. a
lone chord glyph with no string); elements *after* the pivot (leaves)
each independently attach right after whatever precedes them, scoped via
the pivot's class already sitting in their backtrack.

Rules are emitted **most-specific-first** (longest backtrack+lookahead),
matching `jzpbuild/gpos.py`'s established first-match-wins ordering
discipline within a lookup.

One deliberate gap remains and is explicitly patched: `area_fy` has a
"nothing precedes area_right at all" root default (needed so bare `fy`
alone still gets centered), and that rule has *no* context requirement at
all — the lowest-specificity rule possible. Left unguarded, it would also
fire (incorrectly) whenever `area_fy` is followed by anything that isn't
one of this module's own longer matches: a `loki`/`nc`/`tiao`/`mo` word,
or a genuine "blank" (no right hand at all) word with fy+hui/left/jc/zhu
— both of which the classic pipeline already positions for real.
`build.py` adds one explicit mid-specificity "blocker" rule: if `area_fy`
is immediately followed by hui/left/jc/zhu or any other family's
right-hand class (`@area_fy_blocker`, built from classic's own shared
per-family classes), zero it out instead. Every genuine rule above
requires its own per-signifier class (disjoint from this blocker class,
and a subset of classic's per-family class) somewhere in its own context,
so it's always at least as specific and never shadowed by the blocker.

Verified against the full `tests/test_shaping.py` corpus (78 cases) with
gou/io/li live: 0 glyph-name mismatches, 0 position differences for every
case outside this module's scope, and correct (though not always
pixel-identical to classic — see "Known simplifications") output for
every gou/io/li case.

## Per-signifier scoping and `signifiers.py`

Classic `jzpbuild/features.py` defines one glyph class per *family*
(`@area_right__gou = [ lg_gou lg_da ]`) — this module additionally
generates one class per *signifier* (`classes.py`:
`@area_right__gou__lg_gou`, `@area_right__gou__lg_da`, separately), which
is what lets `RELATIONSHIPS`' `gap` overrides tune `lg_gou` and `lg_da`
independently instead of forcing them to share one value. `signifiers.py`
provides the ASCII-key ↔ glyph translation this needs, built by scanning
`components.csv` (via `jzpbuild.data.load_components()`, read-only —
plain `jzpbuild` is unaffected regardless) restricted to
`_RELEVANT_AREAS` (`area_right`, `area_chord`) — **not** every row, since
some input keys are genuinely ambiguous across areas (e.g. `"V"`/`"jiu"`/
`"lun"`/`"banlun"` each name two different glyphs depending on whether
they're in `area_right`/`area_hui` or their vertical-mode `area_char`
variant form; GSUB picks the right one from surrounding context, which
this module has no equivalent of — adding an area to `_RELEVANT_AREAS`
needs an explicit check that it doesn't introduce that kind of collision).

Some pivots are glyphs that live entirely outside `components.csv` —
cuo's `blank_bar` (what `|` substitutes to) is one of
`config.CONTROL_GLYPHS`, wired up via a hardcoded rule in classic
`features.py`'s `gen_liga_feature()` (`sub bar by blank_bar;`), not a
`components.csv` row at all. `signifiers.py` has a small supplementary
table (`KEY_TO_GLYPH["|"] = "blank_bar"`) for exactly this case — add an
entry there whenever a new `LAYOUTS` pivot turns out to be one of these
control glyphs.

`classes.signifier_token` builds FEA class names from the **glyph name**,
not the raw key — a real bug hit while adding `chord_right`: `|` isn't a
valid character inside a FEA identifier, so embedding it directly (as an
earlier version of this code did) produced a `FeatureLibError: Unexpected
character: '|'` at compile time. Glyph names in this pipeline are always
identifier-safe; ASCII keys aren't guaranteed to be.

## cuo: current status (incomplete, read before relying on it)

`chord_left` (`C`/`DC`/`FC`/`TT`) and `chord_right` (`|`) are early,
minimal `LAYOUTS` entries — real progress toward covering cuo, but not
there yet:

- **Neither has `fy`/`left`/`hui` yet.** Classic `cuo_rules()` (in
  `jzpbuild/gpos.py`) supports those on both segments; these entries
  currently only model `chord`/`bar` → (optionally `jc`) → `string`.
  Real cuo words that exercise the missing areas will fall through
  unpositioned by this module.
- **`AREA_SIZES["chord"]`/`["bar"]` are rough placeholders**
  (`chord`: 1000×1000, `bar`: 500×1000) invented for this module, not
  derived from real glyph outlines — and note `bar`'s *width* here isn't
  actually load-bearing for `|`'s own x-placement (`centered_x_left_border()`
  returns the constant `CENTER_X` regardless of `AREA_SIZES`), so retuning
  it alone won't change anything visually. The real increment after typing
  `|` is `blank_bar`'s glyph advance width (`config.CONTROL_GLYPHS`,
  1000 units as of this writing) — a base-glyph metric shared with every
  pipeline, not something this module's `pos` rules touch at all (`build.py`'s
  `_Rule.render` always emits a `0 0` xAdvance/yAdvance component).
- **Double-counting risk under plain `--dynamic_pos`.** Classic
  `gpos.py::cuo_rules()` has no zero/skip mechanism analogous to the one
  `li` needed (see below) — its blocks are only zeroed under
  `--dynamic_pos_only`'s blanket `zero_others`, never under plain
  `--dynamic_pos`. If `chord_left`/`chord_right` ever produce real
  (non-zero) positioning under plain `--dynamic_pos`, it will double-stack
  with classic's own un-zeroed cuo positioning — the exact bug class this
  module's whole design (see "Why not mark attachment") exists to avoid.
  **Test cuo exclusively under `--dynamic_pos_only` until this is fixed.**
- The `chord`/`bar` pivot sits *first* in `order` (`{"pivot": True}` at
  index 0), unlike `default_jzp`'s pivot (last) — confirmed against
  classic `cuo_rules()`, where the chord/bar anchor precedes left/hui in
  the glyph sequence. This is exactly the kind of case the `order`-based
  design (rather than an assumption baked into `build.py`'s code) exists
  to support — an earlier version of `build.py` hardcoded "pivot always
  comes last," which silently produced wrong backtrack/lookahead for a
  pivot-first topology like this one.

## Rule-count scaling (measured, not estimated)

Per-signifier generation means `gou`/`io` now generate roughly double what
a per-family version would (2 signifiers each vs. 1 rule set per family).
Re-measure from the generated `.fea` if you need current exact counts —
the shape of the scaling argument is unchanged from before:

- **More right-hand families** (bringing `loki`/`nc`/`tiao`/`mo` into this
  module): *linear* in family/signifier count.
- **More independently-optional stacking elements** (a slot beyond
  fy/left/hui/jc/zhu): *exponential* — the presence-combination space is
  2^(number of optional elements) per signifier. This is the real cost
  driver, not family count — worth deciding how many more optional slots
  a topology's `order` will realistically need before extending further.

## Adding another family to `default_jzp`'s scope

As of this session, `jzpbuild/genfea.py` imports `RIGHT_KEYS` from
`dynamic_positioning.geometry` (fixed — it used to hardcode `{"gou",
"io"}` independently in two places, which meant changing
`geometry.RIGHT_KEYS` alone would silently no-op). Adding a family to
`RIGHT_KEYS` now genuinely is close to a one-line change, plus:

- A `{"signifiers": [...], "value": ...}` entry for that family's keys on
  any `RELATIONSHIPS` row that's genuinely signifier-specific (currently
  just `right`-attaches-to-`jc`) — missing this raises `KeyError` the
  first time that signifier/combination is hit, not silently.
- `signifiers.keys_for(family)` already works for any family in
  `config.RIGHT_SELECTORS` with `area_right`-tagged `components.csv` rows
  — no separate registration needed there.

## Adding a genuinely new topology

Append a new `LAYOUTS` entry with its own `areas`/`vertical_center_order`/
`relationships`/`order`/`selector` — `build.py`, `classes.py`, and
`anchors.AnchorEngine` are all already driven by `geometry.LAYOUTS`
directly, so a new entry is picked up automatically, no separate
registration anywhere else. See `chord_left`/`chord_right` above for a
real (if incomplete) example, and "cuo: current status" for what's still
missing before a cuo-shaped topology is actually correct.

## Known simplifications (not pixel-perfect, by design)

- Most `RELATIONSHIPS` gap values are explicit placeholders this round
  (see geometry.py's module docstring) — expect retuning.
- `area_zhu`'s attachment to `area_right` and li's `string_top`/
  `string_bottom` gaps are two of the few real numbers actually derived
  from matching classic output; most others are not yet.
- Confirmed **algebraically** (not just empirically) for li: no single
  gap value on the `right`-attaches-to-`hui`/`left` relationship can make
  *both* `area_hui`/`area_left` and `area_right` match classic
  simultaneously for a left+hui+li combo — the whole-stack centering
  shift that would satisfy one is mathematically incompatible with the
  one that satisfies the other. Chose to match `area_right` (the
  technique glyph, most visually load-bearing) and let `area_hui`/
  `area_left` drift in that specific combo.
- Per-area box sizes (`geometry.AREA_SIZES`) are generic constants, not
  derived from real glyph outline bounding boxes (cuo's `chord`/`bar` in
  particular — see "cuo: current status").
- `elem_edge`/`base_edge` default to "elem's far edge, base's near edge"
  (e.g. "elem's top touches base's bottom plus gap") for every
  relationship unless written out explicitly — this covers the vast
  majority of real relationships; the exceptions so far are rare enough
  that they're called out inline in `RELATIONSHIPS` where they occur.
- This module's rule count is not dramatically smaller than the classic
  per-layout enumeration it replaces — the authoring win is in
  `geometry.py`'s declarative table (edit a handful of relationships) vs.
  hand-tuning dozens of Figma layout frames, not raw `.fea` line count.
